## Transaction and recovery details

`ExecuteCombat(command, expectedBindingRevision=-1)` optionally rejects stale outer bindings before invoking the core. Every outer command takes the latest `ActiveCombat.State`, clones the entire profile, reduces once, validates, constructs the next binding, durably writes once, and only then publishes. Every important inner transaction uses the injected sink before publishing its candidate. A cached inner session is invalidated after an outer transition. Runtime must reread `ActiveCombat.State` after a command or Tick; `ProfileState`'s stored combat reference can lag ordinary unsaved simulation frames. `SaveCurrent` always captures the current inner reference.

Reaction deadline resolution uses the same sink. Failure restores the previous inner state, returns zero simulated time, and exposes `LastTickError`; mode elapsed time is rolled back for that tick. `Tick` counts unscaled run duration including focus/roll animation, excluding a manual pause. Safe event time counts toward run duration. Plain simulation frames do not write the complete profile.

`ResolveEncounter` executes production `EndEncounter` on a temporary session with neither Store nor sink, then resolves the objective, reward candidates, ability and tutorial facts in the same outer commit. Pending incoming damage and pending rolls must finish first. Cleared records retain metadata/configuration but drop redundant live/start combat snapshots. Story `RetryStoryEncounter` restores the entire encounter-start snapshot with a new attempt ID, including original RNG and resources. Ordinary combat load keeps current paid results. Challenge has no whole-encounter retry.

Challenge settlement immediately rebinds Story and leaves the Challenge record `Settled`; `meta.lastSettlement` contains its result. Story victory records `STORY_COMPLETE`, remains `Exploring`, and can backtrack. `SettlementOnce` is idempotent; no challenge research is needed to reach Story's fixed objective path.

`TrainParty`: Story only, safe R0, active actor within 6 units of its center, no event/reward pending. Costs 3 research once (`meta.trainingLevel` 0→1). Increases current Story party maxHP and HP by 2 each. A new Challenge copies `ModeState.departureTraining` and applies the corresponding +2 initial HP; an existing Challenge is unaffected. This snapshot participates in the immutable plan hash. Training does not grant Charge or alter class-resource caps.

Before an event's first roll, reopening with a different `actorId` updates the quote. After payment, result/bonus/actor are locked. The original actor may be downed when reopening/confirming an existing result; a paid reroll still requires that original actor to be alive with Inspiration. Closing a result panel never erases or redraws it.

Enemy pattern `angle` is the full cone angle. `EnemyTemplateFor(actorId)` resolves the stable `world.strings["enemyTemplate/" + actorId]` mapping. R4's guard spawn is (55,21), outside the center cover. DungeonConfig.json is generated from the actual default DungeonConfig using Reports/V051_RULE_EXPORT.

`ProfileStore.WriteFault` accepts the existing five `CombatWriteStage` boundaries. It preserves the old committed main file on failure, including faults after replace/verify; a failed first creation is retained as an uncommitted artifact. Load refuses old P0/P1 envelope versions before considering a P2 backup. Backup recovery honors a readable main identity header and rejects a different profile/instance. A completely unreadable main can only be recovered from the validated backup at that same path; temporary files are never save authority.

Load and Save each acquire a per-path cross-process `FileShare.None` handle on `MainPath + ".lock"` before reading authority or touching the shared temporary file. The lock covers validation, revision checks, replacement, verification and any rollback. A competing reader/writer immediately receives an IOException; no waiting or reentrant ownership is allowed. The directory is ensured before opening the lock, and the lock file remains on disk after handle release to avoid deletion/recreation races. A stale writer must still explicitly load the new revision after acquiring ownership later.
